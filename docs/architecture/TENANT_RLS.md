# 数据库租户隔离（S11）

## 运行边界

API/worker 使用独立普通登录角色，继承 `cyshuhe_app` 权限组，不是表所有者，不具备超级用户、BYPASSRLS、建库、建角色或复制权限。生产启动会检查直接权限、可继承的特权角色以及所有带 `org_id` 的业务表是否强制执行 RLS；不满足就拒绝启动。

数据库迁移使用独立维护凭据；API 启动命令不再执行迁移。Compose 的一次性 `migrate` 服务升级结构、配置普通登录角色，API 等其成功后启动。普通 API/worker 容器不获得数据库所有者密码。模型 API Key 仍仅从环境读取。

`app.runtime_role` 是运维命令，不是 HTTP 接口。新部署通过环境变量提供至少 32 个 URL-safe 字符的数据库密码；只发送随机加盐的 SCRAM verifier 给数据库，不把明文密码拼进 DDL 或写入文件。日志不得开启包含认证信息的调试采集。现有特权角色及表所有者拒绝复用。

本地 `dev_local.py` 在迁移与种子操作之后，为 API/worker 改用专用普通角色。本地 pgserver 原有回环 trust 认证不等于已验证生产密码认证；生产 SCRAM 连接仍需在部署阶段实测。维护凭据、普通运行凭据、模型凭据分别管理。

## 受保护数据

以下 11 张表启用 `ENABLE ROW LEVEL SECURITY` 和 `FORCE ROW LEVEL SECURITY`：

- 企业与账号：`organizations`、`users`。
- 分析任务及派生数据：`analysis_tasks`、`analysis_messages`、`analysis_step_traces`、`report_versions`、`analysis_events`。
- 模型调用审计：`llm_call_audit`。
- 报告更新影响与通知：`update_impacts`、`user_notifications`。
- 混合审计：`knowledge_audit_records`。企业脱敏配置等私有记录按企业隔离；未知类型默认不向匿名或其他企业公开。

法规、条款、官方来源、译文、知识图谱等既有公共知识库不改为企业私有。公共法律审计只有明确的类型白名单可以公开读取，不能把任意 `org_id=NULL` 的未知审计当公共资料。普通企业不能伪造公共法律审计。站内通知继续由接口按当前用户过滤，数据库 RLS 兜底的是企业边界，并非每个企业内部岗位的全部权限。

消息、轨迹、报告新增可空 `org_id`，从所属任务回填。历史系统任务仍可为空，只向受信管理/系统身份可见。新增元数据不覆盖原正文、引用、审批、模型输入输出快照或审计哈希。派生记录的数据库触发器检查任务归属，更新影响检查报告归属，通知检查影响、任务与接收人属于同一企业；不能只伪造一个 `org_id` 绕过隔离。

## 身份如何进入事务

1. 请求进入时清空当前数据库上下文，默认拒绝业务数据访问。
2. 登录过程只允许查询当前标准化邮箱及其企业，以校验密码和启用状态；这一临时身份不能改写账号。
3. 受保护请求先验证 JWT 签名/受众。签名中的 subject 仅能查询自己的账号，重新核对角色、企业及停用状态后，才绑定正式身份。请求体、查询参数和 `X-Org-Id` 不能选择企业或管理员模式。
4. SQLAlchemy 每次事务开始用参数化 `set_config(..., true)` 写入事务局部变量。提交、回滚后重新绑定；离开事务后连接池中的企业和管理身份不沿用。空值使用 `NULLIF(...,'')::uuid`，避免连接复用后空字符串转换异常。
5. SSE 每轮重新核对账号及企业状态，再查询有权限的事件；等待网络写入时不占用数据库事务。
6. worker、CLI 只有在明确的运维入口中使用系统身份。用户分析后台任务继承经过验证的请求上下文；模型审计的独立事务使用同一企业边界。

平台管理员和律所复核员保留既有管理端查看范围；具体导入、激活、账号管理等操作仍由接口角色权限控制。RLS 不能替代接口权限。相关 PostgreSQL 行为参考：[行安全策略](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)、[CREATE POLICY](https://www.postgresql.org/docs/16/sql-createpolicy.html)、[SET LOCAL 的事务作用域](https://www.postgresql.org/docs/16/sql-set.html)。

## 威胁边界与后续维护

这层保护解决应用遗漏企业过滤或派生数据归属校验的问题。它信任已验证身份的应用服务及其数据库凭据；不宣称能抵御应用主机被完全控制、数据库所有者/超级用户访问，或允许攻击者执行任意 `SET app.*` 的数据库凭据泄露。SQL 参数化、接口授权、凭据隔离和主机防护仍然需要保留。

生产不得把迁移凭据给 API/worker，不得通过关闭 RLS 排除故障。历史数据存在时迁移拒绝移除隔离元数据；版本回滚应先评估代码与新结构兼容性。增加租户表时必须添加企业归属、RLS 策略、必要的父子约束及普通角色回归；运行时门禁会拒绝缺少强制 RLS 的租户表。

部署、字体、说明书及真实公网环境的整体验证属于 S12。真实法规人工核验和审批继续待核对，RLS 验证不代表法律验收通过。
