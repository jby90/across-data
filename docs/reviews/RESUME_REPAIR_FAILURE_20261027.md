# 分析追问后续跑补证异常修复

日期：2026-10-27。

## 诊断

对用户报告的失败任务执行只读诊断（数据库事务 `READ ONLY`）。该任务在回答业务追问后，按断点只重算 D3、D8，保留其他六个维度的已有提案。随后质检发现 D1、D6 等保留维度仍有原文/OCR 或依据生成问题，需要进入补证。

流水线的 `support_caches` 原先只按本轮初始分析的 `active` 维度建立。补证访问保留维度的缓存时发生 `KeyError: 'D1'`，尚未进入报告编制就已异常终止。兜底错误轨迹却固定挂在报告编制节点，导致界面定位误导。

埃及原文的 OCR 残缺与依据不足是独立的数据质量问题。本次处理续跑状态和补证执行错误，不补写原文，不修改法源，不降低引文、数字或语义核验门槛。

## 修改

1. 为全部业务维度初始化各自独立的本次运行补证缓存。只为实际需要的维度调用模型，保留其他维度结果；不增加正常续跑中的模型调用。
2. 补证前提交真实的 `re_analysis` 阶段事件。异常处理从持久化的最近阶段事件定位节点，并在错误输入快照记录 `failed_phase`、`failed_node_id`，不再统一挂到报告编制节点。
3. 历史任务、回答、断点、证据和审批记录不回写。原有历史错误轨迹保留，后续执行追加新轨迹。
4. 修复隔离测试中一个旧破坏性归档夹具的清理：损坏测试文件后在 `finally` 恢复原始测试字节，避免污染后续使用相同内容哈希的测试；原归档完整性拦截断言保留。

## 验证

- 修改前在独立测试数据库复现同样的错误，堆栈指向 `_support_cache=support_caches[c]`，报 `KeyError: 'D1'`。
- 新增六种续跑修复场景：两个保留维度 × 原提案拒绝、无结论、模型错误。验证仅重算追问维度，再补证需要修复的保留维度；工作流版本和八维度结果完整，原失败记录不被改写。
- 新增两种失败反例：补证仍拒绝时保留分析失败及零引用，不能转为成功或部分样稿；补证发生未预期异常时定位分析节点，保留原断点，发出正确的失败事件。
- 155 项后端回归通过：S6、主分析流水线、工作流版本与执行、引用策略、依据忠实度与模型成本、S5 质量、导出/SSE，以及原有 12 项 S1/S2 反例。
- Ruff 检查与格式检查通过。全部模型行为使用测试替身，没有为了回归调用真实模型，也没有向业务库写入测试资料。

业务任务的真实模型重试由用户在原对话发起；本次不自动重跑并消耗模型额度，也不将已有失败状态改写为成功。
