# S10 来源更新、报告影响与站内提醒

## 实现及数据边界

- 复用采集 worker 和内容哈希去重。发现 URL 先写独立登记，再下载、解析；抓取失败或被 robots/来源条款拦截不伪造成功入库。
- `source_fetch_observations` 记录来源实际返回的归档版本。A→B→A 不覆盖原文，也不把归档序号最大者误当当前抓取结果。检索和语义图谱使用同一来源观察；新版缺少可解析文本时保留缺口。
- `version_changes` 按原章节路径、条号及逐字哈希比较；不能唯一对齐则标记待核对。字节变化但条款一致单独记录。变化记录及观察记录在数据库层禁止更新、删除。
- worker 独立监测循环按 60 秒默认间隔恢复未处理记录，使用数据库事务锁避免多个 worker 重复扫描。后台中断后的报告关联在后续扫描恢复。
- 报告影响逐报告、逐维度记录，截止时间为记录的发现时间加 72 小时。通知按任务、变更和用户去重，八个受影响维度合并展示，提供已读、原报告定位与重新评估。
- 新报告仅在相应维度完成且确实引用当前观察版本时解除操作性影响。缺口或分析失败不能解除。新报告是新版本，原报告正文和原引用快照保留；历史导出另加来源变化提示。
- 新增管理端“更新与时效”、用户端通知列表及铃铛。通知轮询仅在可见页面执行，默认 15 秒；运行进度仍使用 S7 的 SSE。未配置邮件服务，未向任何人发送邮件。
- 本阶段没有真实资料人工审批。既有采集联动对变动条款的旧译文/旧边标记 `stale` 前，会追加完整不可变审批快照；审核人、时间、证据保留，不能继承为新版批准。新增测试逐字段核查这一历史，而非将 `stale` 当作审批丢失。

## 时效口径与限制

- 当前既有模型只有下载、解析、待 OCR、失败及独立人工复核状态，没有“人工发布完成”的历史事件。因此面板如实统计**发现至首次成功解析入库**，与官方公布日、法律生效日及人工复核分别呈现。不能将这一数字宣称为“30 天内完成法律复核发布”。历史没有解析时间的记录保持未知，未回填抓取时间冒充。
- 若 worker 停机或来源被拦截，不能保证实际 72 小时内处理；超期提醒和超期处理会显式计入时效面板，不倒填通知生成时间。
- 差异是来源内容变化的技术记录，不确认法规已经修订或新版已生效。解析缺口、未知版本状态、机器翻译及语义关联仍待人工核对。
- 2GB 级目标服务器仅按原型部署验证，不能据此宣称满足 100 人在线、20 个 AI 报告同时执行的生产容量。

## 手动复测步骤（隔离演示）

1. 用户端登录，打开“更新通知”，确认来源标题明确标记为合成资料，发现时间、72 小时期限和受影响维度可见。
2. 点击“查看报告”，确认定位相同任务，v1 显示来源变化提示；查看引用仍为待核对。
3. 返回通知，标记已读；仅移除未读标记，更新影响仍未解除。
4. 点击“重新评估”，确认进入相同任务并显示运行进度，完成后产生 v2；v1 保持可选。
5. 管理端“更新与时效”刷新，检查待处理、已处理变化，展开来源记录查看原文哈希及条款差异。
6. 切换回 v1，导出 Word/PDF，确认来源变化提示和原历史正文均存在；不得把后续报告内容替换进 v1。

真实五国库地址及模型配置不切换到合成演示库。人工核验继续暂缓；后续 S11 数据库 RLS、S12 全栈部署/字体/说明书、S13 总验收仍需完成。
